# Sections

The core sections come from `new_project.py` (`assets/starter/`). Optional sections are written when the product
needs them. Each entry says what it must contain to be "done". Order in `ds.config.json` = order on the page.

## Core (always)

| id | Contains | Done when |
|---|---|---|
| overview | hero (name, one line of promise, CTA to theme and design.md), a Hairline figure, counts (icons, illustrations, components, screens) | counts are true, line written in the product's voice |
| theme | semantic colours per theme with contrast chips; contrast tables | generated by the build; prose rewritten in source language |
| colors | primitives with provenance; chart palette | `palette_check.py` passes; derived values flagged |
| typography | families, scale, weights, line lengths; pairing reason | sizes only from the scale |
| foundations | spacing, radius, elevation, motion durations and easing, density (comfortable / compact for data-heavy products) | every component uses these lists |
| icons | set + licence, sizes, colour rule, motion vocabulary, the grid of icons used | `icons/SOURCES.md` complete |
| splash | animated SVG splash light/dark, loader, timeline, PWA launch rules | frames checked (start, middle, end) |
| illustrations | Hairline figures mapped to situations (empty, waiting, error, success), usage rules | one figure per situation, each with its place in the product |
| accessibility | `<ds-a11y>` live on the page: principle (preferences, not an overlay), options with WCAG criteria, placement in the product, keyboard, privacy, API (`references/accessibility.md`) | panel works by keyboard, at 200 % text and 390 px; `qa.mjs a11y` passes |
| components | buttons, fields, selects, checkboxes/switches, badges, tabs, segmented, tables, cards, toasts, dialogs, menus, pagination, empty states — every state | keyboard + focus + disabled + error shown |
| integration | tokens CSS, framework mapping (Tailwind theme, CSS variables, the app's icon names), design.md | copy buttons work; mapping matches the codebase |
| notes | decisions, sources, licences, guessed values, open questions | nothing guessed is presented as fact |

## Screen sections: the shape that works
For each product area (e.g. "Products"): an in-section summary (chips linking to sub-parts), then
1. the list/table view (search, filters, bulk actions, pagination, states: loading skeleton, empty, filtered-empty, error);
2. the detail view (header, tabs, the area's key panel);
3. the form (validation after blur or submit, error summary, required source-language fields);
4. the area's signature interaction (drag in a pipeline, stock adjustment, quote lines, booking slots);
5. a spec block: anatomy, rules ("available = in stock − reserved"), accessibility, edition availability,
   mapping to the backend model (field names) when there is one.
Make the demos interactive where it explains behaviour (a filter that filters, a dialog that opens and returns
focus), and static where it does not.
