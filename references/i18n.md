# Languages

The page is written once, in the source language. Other languages come from a dictionary keyed by the source text,
applied in the browser (`assets/runtime/i18n.js`): every visible text node and `aria-label`, `title`,
`placeholder`, `alt`. Content added later by scripts is translated as it appears. Switching takes milliseconds.

## Pipeline
```bash
python scripts/build.py <project>                         # 1. build in the source language
node scripts/i18n_extract.mjs <project> [--size 400]      # 2. i18n/chunks/chunk_NN.json: texts not yet translated
#   3. translate each chunk into i18n/chunks/out_NN.json  {"it": {"<source>": "<translation>"}, "en": {…}}
python scripts/i18n_merge.py <project>                    # 4. i18n/dict.json (+ overrides*.json win)
python scripts/build.py <project> && node scripts/qa.mjs <project> i18n   # 5. rebuild, check
```
Repeat 2–5 after adding sections: only new texts are extracted.

## Register: decided at discovery, written in the glossary, applied everywhere
Before the first word is written, settle with the person the **form of address per language** (fr "vous" or "tu",
it "Lei", "voi" or "tu", de "Sie" or "du", es "usted" or "tú"; English has none) for the interface, for the e-mails
and for the AI assistant separately if they differ, and the **exceptions**: slogans and taglines keep the brand's
own wording (a familiar slogan stays familiar under a formal interface), legal text follows the lawyer. Write it in
`i18n/glossary.md → Style` with one example sentence per language; the source language follows it too (a French
source written in "tu" cannot become a "vous" interface by translation alone). A register changed later means
re-reading every string: decide it once.

## Translating the chunks
- Fill `i18n/glossary.md` first (product terms, names never translated, register, punctuation). Translators —
  you or parallel agents, one chunk each — read it before starting.
- Translate meaning, not words; keep UI labels about the same length; keep leading/trailing symbols (·, →, …).
- Many strings are fragments of a sentence split by a tag (`<b>`, `<code>`, a link): translate each so it reads well
  in place. If word order makes that impossible, rewrite the source with one sentence per language:
  `<span data-i18n-skip><span data-l="fr">…</span><span data-l="it">…</span><span data-l="en">…</span></span>`.
- A string that is a name, a code, a file name or a number comes back unchanged.
- Hand corrections go in `i18n/overrides*.json` (same shape), never in dict.json: the merge rebuilds dict.json.
  An empty value in an output or an override never erases a translation: the merge keeps the earlier one, reports
  the string and exits 1. The same rule holds for any script of yours that converts or extracts text: it never
  replaces a published text by nothing, and it keeps the file's line endings (`scripts/_text.py`).
- Many agents translating at once can hit rate limits: run 2–3 at a time, and make each write its output file
  progressively (every ~100 strings) so a stopped agent loses little.

## Things the dictionary cannot do (do them in the parts)
- **JS-built strings**: `dsT({fr: "Enregistré", it: "Salvato", en: "Saved"})`, and re-render on the `ds:lang` event.
- **Numbers and money**: write them in the source format ("4 800 €"); the runtime re-formats amounts and
  percentages with `Intl` (it: "4.800 €", en: "€4,800"). In JS, format with
  `new Intl.NumberFormat(dsLang(), {style: "currency", currency: "EUR"})`.
- **Dates in words**: `new Intl.DateTimeFormat(dsLang(), {weekday: "long", day: "numeric", month: "long"})`.
- **Punctuation**: French puts a space before `: ; ? !`; the runtime drops it when a translation starts with
  punctuation, but write the source so punctuation stays inside the same text node.
- **Client content** (a sample web page in the site editor, a customer's email) is content, not interface:
  mark it `data-i18n-skip` and keep it in its own language — or show one sample per language.
- **The same word, two meanings** ("Aperçu" = preview / overview): the dictionary has one entry per source
  string, so make the source strings distinct (or use `data-l`).

## Lessons from a large multi-language project
- **Packets of ~250 strings** per translator, with one shared brief listing the decisions already taken: tier
  names, tagline, keyboard key names (Ctrl, Esc…), register per language (tu/vous, tu/Lei), punctuation per
  language, spellings of place names. Add every new decision to the brief at once.
- **Second pass** (new strings only): extract again and give the output files a different prefix (`out2_NN.json`)
  so the first batch is never overwritten.
- **Normalise after the merge** with a short script for mechanical rules (Italian has no space before `: ; ? !`),
  then re-run QA.
- **Extraction must click through interactive states**: tabs, accordions, dialogs, toggles, tooltips and error
  states hold text that a static crawl never sees.
- **Keep whole sentences in one node.** A sentence split by `<b>`/`<a>` translates badly; put the sentence in one
  node, or one `data-l` block per language.
- **Mauritian Creole (`mfe`)**: Latin script, Lortograf Kreol Morisien spelling. Never confuse the code `kr`
  (Korean) with Creole: use `mfe`. Have a native speaker review technical coinages (account, booking, payment)
  before publishing, and list that review as open in Notes.
